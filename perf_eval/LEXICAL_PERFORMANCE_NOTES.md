# Lexical Performance Engineering Notes

## 1. Purpose

This document records exploratory observations that influenced the
formal CPU lexical benchmark methodology for `fortran-nlp-kernels`.

These observations are not part of the final reported benchmark dataset.
They identify performance questions that may require controlled follow-up
experiments.

---

## 2. Implementations under discussion

### Historical FORTRESS implementation

The earlier FORTRESS lexical implementation used:

```text
Python
→ NumPy/F2PY-generated wrapper
→ Fortran lexical_scoring.f90
→ GNU OpenMP runtime


The extension was built locally with Meson using:

GFortran
-O3
-fopenmp
system OpenMP runtime


The build was lexical-only and did not include the vector-search, OpenBLAS, C ABI, or nanobind components of the public package.

Published package implementation

fortran-nlp-kernels==0.1.0b2 uses:

Python
→ nanobind C++ extension
→ stable C ABI
→ Fortran lexical_core.f90
→ GNU OpenMP runtime


The published wheel was built inside a manylinux build environment and repaired with auditwheel. It bundles eligible native runtime libraries, including GNU Fortran, GNU OpenMP, and OpenBLAS libraries.

The package extension contains both lexical and vector-search kernels.

3. Historical F2PY result

A historical FORTRESS development commit recorded the following production-derived replicated workload:

Documents:       17,700
Corpus shingles: approximately 2.53 million


Reported OpenMP results:

6 threads:
    Speedup:     4.98×
    Efficiency: 83.04%

12 threads:
    Speedup:     9.53×
    Efficiency: 79.43%


The machine was an AMD Ryzen 5 5500 with:

Physical cores:      6
Logical processors: 12
SMT threads/core:     2


The twelve-thread result therefore represented full SMT execution.

This result was generated by an unversioned pre-release F2PY extension, not by either published PyPI beta.

4. Published 0.1.0b2 observations

The published fortran-nlp-kernels==0.1.0b2 wheel was later tested through the FORTRESS benchmark on a different replicated workload:

Documents:       24,000
Corpus shingles: 3,309,700
Candidate:       155 shingles
Threads:         12
Warm-up runs:    10
Measured runs:   500


Two consecutive measurements produced:

Run 1
Serial median:   25.557174 ms
OpenMP median:    8.111556 ms
Speedup:           3.1507×
Efficiency:       26.26%

Run 2
Serial median:   25.824195 ms
OpenMP median:    7.879441 ms
Speedup:           3.2774×
Efficiency:       27.31%


The two 0.1.0b2 measurements were internally consistent:

Serial-median difference: approximately 1.0%
OpenMP-median difference: approximately 2.9%


However, the approximately 3.2× twelve-thread speedup was substantially lower than the historical 9.53× F2PY result.

5. Preliminary real-corpus package result

The 0.1.0b2 package was also evaluated on the new combined real corpus:

Base logical documents: 372
Base corpus shingles:   64,577
Replication factor:     10
Scaled documents:       3,720
Scaled corpus shingles: 645,770
Candidate:              faqs-short
Candidate shingles:     20


Results:

Serial median:   1.022616 ms
OpenMP-6 median: 0.314263 ms
Speedup:         approximately 3.25×
Efficiency:      approximately 54.2%


This confirms that the package OpenMP implementation provides meaningful physical-core acceleration on the real variable-length corpus, although the observed scaling differs from the historical F2PY implementation.

6. Important non-equivalence

The historical and current results are not directly comparable because multiple variables changed simultaneously:

Binding technology:
    F2PY
    versus
    nanobind + C ABI

Fortran source:
    lexical_scoring.f90
    versus
    lexical_core.f90 + lexical_c_api.f90

Build environment:
    local compiler
    versus
    manylinux build container

OpenMP runtime:
    system libgomp
    versus
    wheel-bundled libgomp

Extension scope:
    lexical-only extension
    versus
    combined lexical/vector/OpenBLAS extension

Workload:
    17,700 documents and 2.53 million shingles
    versus
    24,000 documents and 3.31 million shingles

System state:
    potentially different CPU load, affinity, frequency, thermal,
    WSL2 scheduling, and background-process activity


Therefore, the current evidence does not establish that any single factor caused the performance difference.

7. Binding-path hypothesis

The F2PY extension generated C and Fortran wrapper code specialized for the Fortran routines.

The package wrapper performs additional explicit operations, including:

NumPy-array validation
offset validation
output-array allocation
nanobind object handling
GIL release and reacquisition
C++ to C ABI transition
C ABI to Fortran transition


This could affect absolute latency.

However, constant wrapper overhead is unlikely by itself to explain the full difference between approximately 9.53× and 3.2× OpenMP speedup, because both the serial and OpenMP package calls use essentially the same wrapper structure.

The binding path remains a hypothesis requiring controlled measurement.

8. OpenMP-runtime hypothesis

The locally compiled F2PY extension likely used the operating system's GNU OpenMP runtime.

The repaired manylinux wheel contains a bundled GNU OpenMP runtime under a package-private native-library directory.

Possible runtime-dependent factors include:

thread-team creation and reuse
thread waiting policy
thread affinity interpretation
SMT placement
barrier behavior
worker wake-up latency
interaction with WSL2 scheduling


The bundled-runtime hypothesis is plausible but unproven.

9. Compiler and portability hypothesis

The local F2PY extension and the published manylinux wheel were built in different compiler environments.

Both used:

-O3
-fopenmp


However, different compiler versions may make different decisions about:

inlining
branch generation
loop optimization
OpenMP outlined functions
register allocation
instruction selection


The manylinux wheel is built for portable Linux compatibility rather than specifically for the AMD Ryzen 5 5500.

No architecture-specific option such as -march=native was used in the published wheel.

The compiler/build-environment hypothesis remains unproven.

10. Background-load discrepancy

During one exploratory session, unrelated processes were consuming significant CPU time:

crm_agent/main.py: approximately 77% CPU
VS Code cpptools:  approximately 37% CPU


This created visible logical-CPU saturation and could affect:

OpenMP worker scheduling
thread migration
P95 latency
barrier completion
CPU boost frequency
measured parallel efficiency


Those processes were stopped before beginning the formal benchmark.

Exploratory measurements collected under mixed system-load conditions must not be included in the formal result tables.

11. Published 0.1.0b1 observation

An attempt to install and execute the published 0.1.0b1 wheel in the current environment resulted in a segmentation fault during the FORTRESS lexical benchmark.

The 0.1.0b1 wheel is therefore excluded from performance comparison.

No performance conclusion should be drawn from the failed execution.

The formal benchmark baseline is:

fortran-nlp-kernels==0.1.0b2

12. Controlled diagnostic required for causal attribution

A future diagnostic should evaluate three implementations using exactly the same candidate, packed corpus, offsets, machine state, OpenMP settings, warm-up procedure, and repetitions:

A. Historical/local F2PY extension
B. Locally compiled fortran-nlp-kernels 0.1.0b2
C. Published manylinux fortran-nlp-kernels 0.1.0b2 wheel


The diagnostic should proceed incrementally:

A versus B:
    isolates wrapper and source-structure differences while keeping
    compilation local

B versus C:
    isolates local-build versus manylinux-wheel differences

System libgomp versus bundled libgomp:
    investigates OpenMP runtime behavior

Identical local compiler flags:
    controls compiler optimization differences


This diagnostic is separate from the primary package benchmark.

13. Formal benchmark decision

The formal CPU lexical evaluation will use only:

fortran-nlp-kernels==0.1.0b2


Reasons:

publicly available through PyPI
immutable release artifact
tested manylinux wheels
documented package version
reproducible installation
complete serial, OpenMP, and batched lexical interfaces


The historical F2PY results will not be mixed into the formal package performance tables.

The formal physical-core experiment will compare:

Fortran serial
OpenMP-1
OpenMP-2
OpenMP-4
OpenMP-6


A separate SMT sensitivity experiment will compare:

OpenMP-6
OpenMP-8
OpenMP-12

14. Current interpretation

The current evidence supports these limited conclusions:

The published package produces correct and numerically equivalent serial, OpenMP, and batched OpenMP results on the real corpus.

The published package achieves meaningful OpenMP acceleration on the real variable-length corpus.

The historical F2PY implementation achieved substantially stronger twelve-thread scaling under a different build and workload context.

The performance gap cannot yet be attributed specifically to F2PY, nanobind, the C ABI, compiler differences, bundled libgomp, or workload differences.

The difference is a legitimate performance-engineering question, but it must not delay the reproducible 0.1.0b2 benchmark.
